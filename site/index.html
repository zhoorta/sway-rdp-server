A Linux desktop over RDP, out of the box.

One apt install on Debian 13 or Ubuntu 26.04 (amd64 or arm64). Every account that logs in gets its own desktop, with a shell, a dock and its apps, kept alive between connections. No GPU, no client to install: use the Windows App, Remmina or any RDP client.

install–□✕
$ curl -fsSLO https://waydesk.dev/apt/waydesk-repo.deb
$ sudo apt install ./waydesk-repo.deb
$ sudo apt install waydesk
$ sudo waydesk-setup-admin

Free software, early. Tested with FreeRDP and the Windows App on macOS.

Built to stay light and fast

Most of the work is in not wasting what a server has: memory, CPU and a slow link. Every figure has its method under Measurements.

slow or lossy links–□✕

TCP BBR for the connection

On a distant link with about 4 % loss the connection went from 0.3 to 2 to 4 Mbit/s, and typing stopped arriving in bursts.

flow control–□✕

The picture follows the link

Frames and bytes in flight follow the path; the video bitrate follows what the link delivers, from 300 kbit/s to 10 Mbit/s.

H.264–□✕

Tuned for screens, in software

Screen-content mode, only the changed rectangles: about half the bandwidth of the camera mode. No GPU.

pointer–□✕

The pointer has no delay

The client draws it with its real shape, so it moves at once; only the shape arrives a round trip late.

memory–□✕

Ceilings, compressed swap, a refusal

A memory ceiling per account, compressed swap, and a refusal when the machine is full: 7 to 8 heavy sessions on 8 GB.

isolation–□✕

One session per account

Each account in its own session and systemd slice; the daemon has no privileges, and a small root helper starts sessions.

Your applications run as they are

Wayland or X11, from the distribution or from Flathub: nothing to port.

X11–□✕

X11 applications run

Applications that only speak X11 run through XWayland, one server per account, closed to the others. Checked with CoreX, xeyes and GIMP.

Flathub–□✕

Flatpak, out of the box

Flathub works as it is. Checked: Chromium, VS Code, LibreOffice Calc, Obsidian, Slack, GNOME Text Editor and GIMP.

windows–□✕

Real windows

Title bars with minimize, maximize and close in the theme's colours (dark or light), soft shadows, and a dock that bounces while an app starts.

keyboard–□✕

Your keys, where they are

The layout follows the client. A keyboard that sends its keys to other places, such as a MacBook's through the Windows App, gets its own in the Keyboard window, and the session follows at once.

Connect your way

The port is closed to the network until you open it. waydesk-setup-admin asks how you will connect; waydesk-admin access changes it later (docs/ACCESS.md).

this machine or an SSH tunnel–□✕

The default default

Listens on 127.0.0.1 only. One ssh -L and the client connects to localhost.

a local network–□✕

Directly, on a LAN

waydesk-admin access lan opens the port to this network only; other addresses are closed before TLS.

a VPN–□✕

WireGuard recommended

vpn init, then vpn add NAME: a client with a QR code. vpn remove cuts one off.

a certificate–□✕

One you can verify

cert local-ca makes an authority of your own; clients import it once and check every connection.

Architecture

Three parts with different rights: the network-facing daemon has none, a small root helper checks passwords and starts sessions, and each session runs as the account itself.

runs as waydesk, no privileges–□✕

waydesk

does TLS, the RDP protocol, channel framing, rate limits per address.

never touches user files, calls PAM, keeps a password after the check.

runs as root, no network–□✕

waydesk-helper

does checks the password through PAM, starts and finds sessions, admits or refuses by memory.

never parses RDP or TLS, listens on the network.

runs as the account–□✕

waydesk-session@UID

does its sway, capture, encoder, input, audio, clipboard, hooks.

never anything as another user.

A session is a systemd unit of the account: it survives a disconnect, sits in user-UID.slice (limits there apply) and is killed with its control group. A second login from the same account takes the running session over. Design notes: docs/MULTIUSER-DESIGN.md.

Security

threat model–□✕

The login is the account's password inside TLS, with no second factor: keep the port off the open internet. The daemon has no privileges, a small root helper starts the sessions, and each account is isolated from the others. This is not an audited product: four internal review passes are written down, with what is still open.

  • docs/THREAT-MODEL.md: who is assumed hostile, and the open items
  • docs/SECURITY-REVIEW.md: the internal reviews
  • docs/ACCESS.md: who can reach the port, certificates, the VPN

Limits

known limits–□✕
  • Early software. Tested with FreeRDP and the Windows App on macOS; Microsoft Remote Desktop (Windows) and mstsc were not tested.
  • No GPU: applications that insist on one do not start. Zed fails with "Failed to create surface"; VS Code and LibreOffice work.
  • Sizing: on an 8 GB, 4-core server count 7 to 8 users with Chromium, Calc and VS Code open if most are idle. Someone compiling or recalculating needs more, and the server refuses a new session instead of slowing everyone down.
